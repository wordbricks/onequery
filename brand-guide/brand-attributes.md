# Brand Attributes

OneQuery is a developer-first infrastructure product for controlled data access.
It gives people and agents one governed way to query approved sources without
scattering credentials or bypassing auditability.

These attributes define how OneQuery should feel across product UI, docs,
marketing, diagrams, screenshots, and generated assets.

## Core Attributes

### Precise

OneQuery should feel exact. It names the source, boundary, policy, state, and
result instead of relying on generic trust language.

Use precision when describing:

- Query validation
- Source access
- Credential ownership
- Connector location
- Audit history
- Cost limits
- Agent boundaries

Avoid abstract claims like "secure by design" when a more concrete mechanism is
available.

### Calm

OneQuery should not feel loud, playful, or urgent. The product exists around
sensitive systems, production data, credentials, and agent access. It should
lower the temperature.

Calm does not mean passive. It means the product sounds and looks composed even
when it is blocking a query, reporting a failed connector heartbeat, or showing
a cost limit.

### Accountable

Trust comes from evidence. OneQuery should consistently surface records,
states, and constraints:

- What ran
- Who or what requested it
- Which source was used
- Which policy applied
- What was returned
- What was blocked

The brand should make accountability feel normal, not punitive.

### Developer-First

OneQuery speaks to developers first. It should respect implementation detail,
workflow ownership, and operational reality.

Developer-first copy and design should:

- Prefer exact nouns over broad category language
- Show real product states instead of abstract metaphors
- Keep setup and next steps clear
- Treat CLI, API, connector, and web UI surfaces as first-class
- Avoid "no-code" framing unless a specific surface warrants it

### Agent-Ready

Agent-ready is a core brand attribute. OneQuery should make agent access feel
bounded, inspectable, and production-aware.

The brand should never suggest that agents get unrestricted access or magical
understanding. The stronger position is that agents operate through the same
approved sources, limits, policies, and audit history as humans.

### Quietly Technical

OneQuery should look and sound technical without becoming dense. The brand can
use terms like connector, source policy, audit log, query validation, and
runtime when they clarify the product.

Avoid explaining obvious engineering concepts to developers. Explain OneQuery's
specific behavior.

## Brand Tension

OneQuery balances several tensions:

| Tension | OneQuery Position |
| --- | --- |
| Powerful vs. permissive | Powerful through explicit boundaries |
| AI-ready vs. AI-hyped | Agent access through governed workflows |
| Technical vs. dense | Exact, but edited |
| Calm vs. invisible | Quiet, but clearly intentional |
| Safe vs. slow | Guarded without feeling bureaucratic |
| Self-hosted vs. managed | Clear about where control lives |

## Messaging Pillars

### One Governed Query Path

OneQuery connects approved data sources behind one interface for developers,
teams, and agents.

Use when explaining the product at the highest level.

Example:

> One governed query path for the data tools your team already uses.

### Credentials Stay Controlled

OneQuery should make credential centralization and connector boundaries visible.

Use when describing trust, self-hosting, and connector architecture.

Example:

> Keep credentials centralized while connectors run where your data already
> lives.

### Agent Access With Boundaries

Agent access should be framed as controlled execution, not autonomous power.

Use when writing about AI workflows, agent tooling, and safe automation.

Example:

> Let agents query approved sources through validation, limits, and audit
> history.

### Every Query Leaves Evidence

Auditability is a core proof point. OneQuery should make query history feel like
a normal part of the workflow.

Use when describing reliability, governance, and collaboration.

Example:

> See what ran, which source it used, and what happened next.

## Decision Rules

When a brand decision is unclear, choose the option that:

1. Makes the product behavior more legible
2. Keeps the interface calmer
3. Uses current documented capability instead of future promise
4. Shows real product proof instead of decoration
5. Treats agent access as bounded and auditable
6. Respects developer context and time

## What To Avoid

- AI magic language
- Unbounded automation claims
- Generic enterprise security language
- Decorative gradients and abstract worlds
- Friendly mascot behavior beyond the icon itself
- Overly warm editorial storytelling
- Claims about cloud, enterprise, NL to SQL, or compliance unless the exact
  current capability is being documented
